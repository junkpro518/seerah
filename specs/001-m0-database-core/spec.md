# Feature Specification: م٠ — نواة قاعدة البيانات (M0 Database Core)

**Feature Branch**: `001-m0-database-core`

**Created**: 2026-06-19

**Status**: Draft

**Input**: نواة قاعدة بيانات موسوعة السيرة النبوية الموثّقة على Supabase/Postgres: مخطط أساسي + أدوار + بوابة مراجعة إلزامية + تدقيق شامل + تعدد لغات، تُبنى بـ TDD (pgTAP). لا واجهة ولا محرّر ولا صفحات عرض في هذه المرحلة.

> **مصدر القرارات:** `docs/CONCEPT.md` (٤٣ لبنة) و`docs/GAPS.md`. هذه المواصفة تترجم نطاق م٠ (HANDOFF §6) والقرارات ٣٣–٤٣ إلى متطلبات قابلة للاختبار. لا تعيد فتح ما حُسم.
> **حدود المواصفة:** تصف *ماذا* تضمنه نواة البيانات و*لماذا*؛ تفاصيل *كيف* (DDL، RLS، triggers، صيغة JSON، آلية الإشعار) تُحسم في طور `plan`.

## Clarifications

### Session 2026-06-19

- **س١ — شكل جداول الترجمة:** جدول ترجمة **لكل كيان** (`event_translations`, `person_translations`, `location_translations`, `claim_translations`) بمفتاح فريد (entity_id, lang). [معتمد]
- **س٢ — القوائم الثابتة:** **جداول مرجعية (lookup)** لا ENUM. كل صف: `code` ثابت (المفتاح الذي يُشار إليه) + تسميات مترجَمة لكل لغة + لون اختياري. قواعد العمل وقيود CHECK وآلة الحالات تشير إلى `code` لا إلى التسمية المعروضة. [معتمد + توجيه ٢]
- **س٣ — طبقتا المراجعة (نهائي، س٥ + تنقيح المالك):** (أ) **الهيكل/الحقيقة** يأخذ السلسلة الكاملة `draft→submitted→shariah_approved→approved→published` (شرعي ثم تحريري ثم نشر)؛ (ب) **الترجمة لكل لغة** تحريرية فقط `draft→submitted→approved→published` (لا إعادة مراجعة شرعية — الحكم محايد لغويًا)، واستثناء المقدّس عبر `needs_revision` القائم. **الظهور(L)** = الهيكل published AND ترجمة L published (وإلا رجوع للعربي مع تنبيه — لبنة ٣٤). [معتمد]
- **س٤ — 2FA:** جاهزية المخطط + علَم الحالة + سياسة RLS تتطلبه في م٠؛ و**التفعيل الكامل (TOTP) إلزامي قبل أول دخول لعضو فريق حقيقي** — لا ينزلق لما بعد م١. [معتمد + توجيه ٤]
- **توجيه ١ — نموذج ربط المعلومة بالنص (لبنة ٣٣، الأهم):** يجب أن يدعم مخطط م٠ النموذج كاملًا: حقيقة مشتركة (مصدر/درجة مرة واحدة) + نص لكل لغة + إشارات داخل نص كل لغة تشير لمعرّفات المعلومات المشتركة + ترقيم `[n]` مشتق لكل لغة حسب ترتيب الظهور — بحيث لا يحتاج ربطُ المحرّر (م١) أي migration لاحق. [معتمد]
- **بيئة الاختبار (صقل قرار ٢٠):** حلقة pgTAP تعمل على قاعدة Postgres **محلية زائلة** (Docker عبر `supabase start`، تُصفَّر بحرية)، والترحيلات المعتمدة تُدفع للسحابي عبر `supabase db push`. السحابي **لا يُصفَّر إطلاقًا** (مبدأ VI)؛ Docker مختبر اختبار مؤقت لا استضافة. [معتمد — دستور v1.0.1]

## User Scenarios & Testing *(mandatory)*

> الفاعلون: **كاتب** (author) · **مراجع شرعي** (shariah_reviewer) · **محرّر/معتمِد** (editor) · **مدير** (admin) · **زائر** (anon) · **النظام** (ضمانات السلامة والتدقيق). كل قصة قابلة للاختبار باستقلال عبر اختبارات pgTAP على قاعدة البيانات وحدها.

### User Story 1 - بوابة المراجعة الإلزامية لا تُتجاوز (Priority: P1)

أي محتوى (حدث/شخص/مكان/معلومة/ترجمة) يبدأ مسودة ولا يصل "منشور" إلا بعد المرور بـ مراجعة شرعية ثم اعتماد تحريري. لا أحد — **حتى المدير** — يستطيع نشر شيء يتخطّى الطبقتين. الزائر لا يرى إلا المنشور.

**Why this priority**: هذا قلب مصداقية المشروع (مبدأ III). بدونه تنهار كل ضمانات الجودة، وأي تسريب لمحتوى غير مُراجَع ضرر مباشر.

**Independent Test**: عبر pgTAP: محاولة تحوّل حالة غير مسموح (مثل مسودة→منشور مباشرة) تُرفض؛ محاولة المدير النشر دون مرور الطبقتين تُرفض؛ استعلام بدور anon يعيد الصفوف المنشورة فقط.

**Acceptance Scenarios**:

1. **Given** سجل محتوى بحالة "مسودة"، **When** يحاول أي دور نقله مباشرة إلى "منشور"، **Then** يرفض النظام التحوّل (تحوّل غير مسموح في آلة الحالات).
2. **Given** سجل اجتاز "مراجعة شرعية" ولم يُعتمد تحريريًا، **When** يحاول مدير نشره، **Then** يُرفض النشر.
3. **Given** سجلات بحالات مختلطة، **When** يستعلم زائر (anon)، **Then** يرى المنشورة فقط ولا يرى المسودات/قيد المراجعة.
4. **Given** سجل مُراجَع، **When** يُسجّل النظام هوية المُراجِع، **Then** لا تُعدّ المراجعة "فعلية" إلا بوجود مُراجِع مؤهّل مسجّل (R2) — لا شارة بلا مُراجِع.

### User Story 2 - لكل معلومة مصدرها ودرجتها (Priority: P1)

لا تدخل معلومة مفردة (claim) النظام بلا استشهاد واحد على الأقل ودرجة توثيق؛ وكل معلومة من نوع "حكم" تحمل **مصدر حكم (`grading_source`) غير فارغ**. المصادر نفسها تُعتمد قبل استخدامها.

**Why this priority**: مبدأ I + II — التوثيق على مستوى المعلومة هو ما يميّز الموسوعة. قيد على مستوى قاعدة البيانات، لا اتفاق نوايا.

**Independent Test**: عبر pgTAP: إدراج معلومة بلا استشهاد يُرفض؛ إدراج معلومة نوعها "حكم" بـ `grading_source` فارغ/NULL يُرفض؛ إدراج معلومة بلا درجة توثيق يُرفض.

**Acceptance Scenarios**:

1. **Given** معلومة جديدة، **When** تُحفظ بلا أي استشهاد مرتبط، **Then** يرفض النظام (لا معلومة بلا مصدر).
2. **Given** معلومة نوعها "حكم"، **When** تُحفظ بـ `grading_source` فارغ، **Then** يُرفض الحفظ.
3. **Given** مصدر لم يُعتمد بعد، **When** يُستشهد به في معلومة، **Then** يمنع/يُعلَّم النظام الاستخدام حتى الاعتماد.
4. **Given** معلومة مرتبطة بعدة استشهادات، **When** تُحفظ، **Then** يُحفظ لكل استشهاد **نوع علاقته** (أساسي/داعم/رواية بديلة/مختلف فيه/ضعيف).

---

### User Story 3 - التدقيق الشامل غير القابل للعبث (Priority: P1)

كل عملية (إضافة/تعديل/حذف ناعم) على أي جدول محتوى تُسجَّل في `audit_log` بالقيمة القديمة والجديدة كاملةً (JSONB) والمستخدم والوقت والجدول والمعرّف — حتى تغيير تشكيل حرف. تُسجَّل أيضًا جلسات دخول/خروج الإداريين. وجدول التدقيق نفسه **append-only**: لا UPDATE ولا DELETE عليه **حتى للمدير**.

**Why this priority**: مبدأ IV — محتوى يدوي لا يُعوَّض ومسؤولية علمية. سلامة السجل شرط للثقة والرجوع.

**Independent Test**: عبر pgTAP: أي تعديل على صف محتوى يُنتج صف تدقيق مطابق (قديم/جديد)؛ محاولة UPDATE أو DELETE على `audit_log` بأي دور (بما فيه admin) تُرفض؛ تغيير حرف تشكيل واحد يُلتقط.

**Acceptance Scenarios**:

1. **Given** صف محتوى، **When** يُعدَّل أي حقل (ولو تشكيل حرف)، **Then** يُسجَّل صف تدقيق فيه القيمة القديمة والجديدة كاملة والمستخدم والوقت.
2. **Given** صف في `audit_log`، **When** يحاول المدير تعديله أو حذفه، **Then** يُرفض (append-only مفروض على مستوى الصلاحيات).
3. **Given** جلسة إداري، **When** يسجّل دخولًا أو خروجًا، **Then** يُسجَّل الحدث في التدقيق.
4. **Given** حذف ناعم لصف، **When** يُضبط `deleted_at`، **Then** يُسجَّل ذلك كعملية في التدقيق ويبقى الصف محفوظًا.

---

### User Story 4 - متعدد اللغات من التصميم (Priority: P2)

البيانات مقسّمة طبقتين: **هيكل** (لا يتغيّر باللغة: الروابط، الترتيب، الثقة، إشارات المصادر، درجة المعلومة — مرة واحدة) و**نصوص** (لكل لغة: عنوان/ملخص/سرد/نص معلومة/slug + حالة مراجعة مستقلة). العربية أصل؛ والترجمة تظهر بعد نشرها فقط، وإلا يُشار إلى الرجوع للعربية.

**Why this priority**: مبدأ V — إقحام تعدد اللغات لاحقًا يفرض إعادة هيكلة مكلفة. يُبنى من الأساس وإن أُدخل العربي أولًا.

**Independent Test**: عبر pgTAP: لكل كيان نصّي جدول ترجمة بمفتاح (entity_id, lang) فريد؛ ترجمة بحالة غير منشورة لا تُعدّ متاحة بلغتها؛ المعلومة (claim) تحتفظ بمصدرها/درجتها في الهيكل مرة واحدة بينما نصّها في طبقة النصوص لكل لغة.

**Acceptance Scenarios**:

1. **Given** حدث بنص عربي منشور وترجمة إنجليزية "مسودة"، **When** يُطلب باللغة الإنجليزية، **Then** تُعدّ الإنجليزية غير متاحة (يُرجَع للعربية مع إشارة)، ولا تظهر حتى تُنشر.
2. **Given** معلومة (claim)، **When** تُترجم لعدة لغات، **Then** يبقى مصدرها ودرجتها واحدًا مشتركًا، ويتعدّد نصّها وslugها وحالة مراجعتها لكل لغة.
3. **Given** كيان نصّي، **When** يُدرَج نصّان بنفس (entity_id, lang)، **Then** يُرفض التكرار (تفرّد لكل لغة).
4. **Given** ترجمة، **When** تُنشأ، **Then** تمرّ ببوابة المراجعة الخاصة بها (نفس آلة الحالات).

---

### User Story 5 - صون البيانات وسلامة الربط (Priority: P2)

لا حذف نهائي أبدًا (حذف ناعم عبر `deleted_at`). كل معلومة ترتبط بحاوية **واحدة فقط** (event أو person أو location) عبر أعمدة منفصلة مع قيد "واحد فقط مملوء". لكل كيان نصّي عمود `body_plain` نص مجرّد يُشتق تلقائيًا من النص الغني للبحث لاحقًا.

**Why this priority**: مبدأ VI — منع فقد بيانات لا تُعوَّض وضمان سلامة مرجعية حقيقية (بدل مرجع متعدد الأشكال الغامض).

**Independent Test**: عبر pgTAP: مسار الحذف يضبط `deleted_at` ويُبقي الصف؛ معلومة بصفرٍ أو اثنين من روابط الحاوية تُرفض (واحد بالضبط)؛ `body_plain` يُملأ/يُحدَّث تلقائيًا عند حفظ النص الغني.

**Acceptance Scenarios**:

1. **Given** صف، **When** يُطلب حذفه، **Then** يُضبط `deleted_at` ويختفي من العرض الافتراضي ويبقى مخزّنًا (لا DELETE فيزيائي).
2. **Given** معلومة، **When** تُحفظ وقد امتلأ عمودا ربط (event_id و person_id معًا)، **Then** تُرفض (قيد "واحد فقط").
3. **Given** معلومة، **When** تُحفظ بلا أي رابط حاوية، **Then** تُرفض.
4. **Given** نص غني لكيان، **When** يُحفظ أو يُحدَّث، **Then** يُشتق `body_plain` منه تلقائيًا.

---

### User Story 6 - الأدوار والوصول الآمن (Priority: P2)

أربعة أدوار (author/shariah_reviewer/editor/admin) من م٠، بصلاحيات أقل-امتياز مفروضة عبر RLS. المدير يدعو الأعضاء ويعيّن أدوارهم. مصادقة ثنائية (2FA) إلزامية لكل صاحب صلاحية كتابة/مراجعة/إدارة. anon للقراءة من المنشور فقط.

**Why this priority**: مبدأ VIII — حماية المحتوى غير المنشور وحسابات الصلاحية.

**Independent Test**: عبر pgTAP/سياسات: كاتب لا يستطيع اعتماد أو نشر؛ مراجع شرعي لا ينشر؛ محرّر لا يتخطّى المراجعة الشرعية؛ anon لا يكتب ولا يقرأ غير المنشور؛ تعيين الأدوار محصور بالمدير.

**Acceptance Scenarios**:

1. **Given** كاتب، **When** يحاول اعتماد/نشر محتوى، **Then** يُرفض (خارج صلاحيته).
2. **Given** مراجع شرعي، **When** ينهي المراجعة الشرعية، **Then** يحوّلها لاعتماد تحريري فقط، لا للنشر.
3. **Given** مستخدم بلا 2FA مفعّلة، **When** يحاول فعلًا يتطلب صلاحية كتابة/مراجعة/إدارة، **Then** يُمنع حتى تفعيل 2FA.
4. **Given** مستخدم غير مدير، **When** يحاول تعيين دور لعضو، **Then** يُرفض.

---

### User Story 7 - الملاحظات الداخلية وخطّافات التكامل (Priority: P3)

`content_notes` مرتبطة بأي كيان (سبب تصنيف/خلاف علمي/ملاحظة تحريرية/للمراجع/سبب رفض)، مخفية عن الزائر افتراضيًا مع حقل `is_public` للنادر المعروض. ومن سجل التدقيق تنطلق **خطّافات** (نقاط تكامل) لإشعارات تيليجرام وتصدير أسبوعي للنسخ/السجلات إلى NAS — الخطّاف موجود من م٠ وإن اكتمل الإرسال الفعلي لاحقًا.

**Why this priority**: لبنة ٢٤/٢٥/٢٦/٤٣ — تخدم بوابة المراجعة، وتؤسّس التكامل دون بناء التسليم الكامل الآن.

**Independent Test**: عبر pgTAP: ملاحظة غير عامة لا تظهر لـ anon؛ الأحداث المهمة في التدقيق تُلتقط بشكل يتيح استهلاكها لاحقًا (نقطة الخطّاف موجودة)؛ مسار التصدير الأسبوعي معرّف كمهمة قابلة للجدولة.

**Acceptance Scenarios**:

1. **Given** ملاحظة `is_public=false`، **When** يستعلم anon، **Then** لا يراها.
2. **Given** حدث مهم (دخول إداري/رفع للمراجعة/اعتماد/نشر/رفض/اعتماد مرجع)، **When** يُسجَّل في التدقيق، **Then** يكون قابلًا للالتقاط عبر نقطة خطّاف الإشعار.
3. **Given** نهاية الأسبوع، **When** تعمل مهمة التصدير، **Then** تُصدَّر السجلات/النسخة إلى وجهة NAS خارجية (الإعداد الفعلي للوجهة وقت التنفيذ).

---

### User Story 8 - الترتيب الزمني للأحداث (Priority: P3)

لكل حدث `timeline_order` (عدد صحيح يدوي = الترتيب الحقيقي) مستقل عن دقة التاريخ، وسنة تقريبية موقّعة (قبل الهجرة سالبة/بعدها موجبة) للتجميع والعرض حسب الحقبة فقط.

**Why this priority**: لبنة ٣٥ — يفصل ترتيب السرد عن يقين التأريخ.

**Independent Test**: عبر pgTAP: ترتيب الأحداث يتبع `timeline_order` لا السنة؛ يُقبل تخزين سنة سالبة (قبل الهجرة)؛ تغيير دقة التاريخ لا يغيّر الترتيب.

**Acceptance Scenarios**:

1. **Given** حدثان، **When** يُرتّبان، **Then** يحكم الترتيبَ `timeline_order` لا السنة التقريبية.
2. **Given** حدث قبل الهجرة، **When** تُخزَّن سنته، **Then** تُقبل القيمة الموقّعة (سالبة).

---

### Edge Cases

- محاولة تحوّل حالة غير موجود في آلة الحالات (مثل "منشور"→"مسودة" دون مسار مسموح) → تُرفض.
- معلومة "حكم" بـ `grading_source` فيه مسافات فقط → تُعامل كفارغة وتُرفض.
- ترجمة منشورة للغة، ثم سحبها (رجوع لحالة سابقة) → تختفي بلغتها ويُرجَع للعربية مع إشارة.
- حذف ناعم لكيان له معلومات/ترجمات → تتبع سياسة متسقة (تظهر/تختفي) دون فقد بيانات أو يتم منع الحذف إذا خالف السلامة.
- محاولة كتابة في `audit_log` يدويًا بقيم مزيّفة → الكتابة محصورة بآلية التدقيق لا بإدخال المستخدم المباشر.
- مستخدم عُيّن له دور ثم سُحب أثناء جلسة مفتوحة → الصلاحيات تُقيَّم لحظيًا عبر RLS.
- إدخال نص بلغة غير مدعومة بعد (قيمة lang غير معرّفة) → يُرفض/يُقيَّد بقائمة اللغات.

## Requirements *(mandatory)*

### Functional Requirements

**الكيانات والمخطط**

- **FR-001**: يجب أن يوفّر النظام كياناتٍ لطبقة الهيكل: `events` · `persons` · `locations` · `sources` · `citations` · `claims` · `claim_citations` · `event_persons` · `event_locations` · `profiles` · `content_notes` · `audit_log`.
- **FR-002**: يجب أن يُعامَل النبي ﷺ كسجل "شخص" عادي (لا كيان خاص في البيانات).
- **FR-003**: يجب أن توجد قوائم/مرجعيات ثابتة لـ: درجة التوثيق، حالة المراجعة، ثقة التاريخ، ثقة المكان، نوع المعلومة، نوع علاقة الاستشهاد، والأدوار.

**تعدد اللغات (مبدأ V)**

- **FR-004**: يجب فصل البيانات إلى طبقة هيكل (لا تتغيّر باللغة) وطبقة نصوص لكل لغة.
- **FR-005**: يجب أن يملك كل كيان نصّي (events/persons/locations/claims على الأقل) جدول نصوص/ترجمة بمفتاح فريد (entity_id, lang) يحوي العنوان/الملخص/النص/الـslug.
- **FR-006**: يجب أن تحمل كل ترجمة **حالة مراجعة مستقلة** وslug مستقلًا لكل لغة.
- **FR-007**: يجب اعتبار العربية اللغة الأصل؛ وألّا تُتاح ترجمةٌ بلغتها إلا بعد بلوغها حالة "منشور"؛ وإلا يُعرض الأصل العربي مع إشارة عدم توفّر الترجمة.
- **FR-008**: يجب أن تكون المعلومة (claim) حقيقةً مشتركة: مصدرها ودرجتها في طبقة الهيكل مرة واحدة، ونصّها في طبقة النصوص لكل لغة.

**المعلومة المفردة والتوثيق (مبادئ I, II, VI)**

- **FR-009**: يجب أن ترتبط كل معلومة بحاوية **واحدة فقط** عبر أعمدة منفصلة (event_id/person_id/location_id) مع قيد "واحد فقط مملوء" مفروض في قاعدة البيانات.
- **FR-010**: يجب ألّا تُحفظ معلومة بلا استشهاد واحد على الأقل (لا معلومة بلا مصدر).
- **FR-011**: يجب أن تحمل كل معلومة درجة توثيق من القائمة المعتمدة.
- **FR-012**: يجب أن تحمل كل معلومة من نوع "حكم" حقل `grading_source` **غير فارغ**، مفروضًا بقيد قاعدة بيانات (يرفض NULL والفراغ).
- **FR-013**: يجب أن يربط `claim_citations` المعلومة باستشهاداتها مع **نوع علاقة** لكل استشهاد (أساسي/داعم/رواية بديلة/مختلف فيه/ضعيف).
- **FR-014**: يجب أن تمرّ المصادر ببوابة اعتماد، وألّا تُستخدم في الاستشهاد قبل اعتمادها.
- **FR-015**: يجب أن يخزّن كل كيان نصّي محتواه القابل للربط الذكي لاحقًا بصيغة نص غني، مع عمود `body_plain` نص مجرّد يُشتق منه **تلقائيًا** عند الحفظ للبحث.
- **FR-016**: يجب أن يحمل كل استشهاد موضعه داخل المصدر (مثل المجلد/الصفحة/رقم الحديث).

**الترتيب الزمني (لبنة ٣٥)**

- **FR-017**: يجب أن يملك كل حدث `timeline_order` صحيحًا يدويًا يحكم الترتيب الحقيقي مستقلًا عن دقة التاريخ.
- **FR-018**: يجب أن يدعم الحدث سنة تقريبية **موقّعة** (سالبة قبل الهجرة/موجبة بعدها) لأغراض التجميع/العرض فقط.

**الحذف الناعم (مبدأ VI)**

- **FR-019**: يجب أن تدعم كل الجداول الحذف الناعم عبر `deleted_at` (أو ما يعادله)، وأن يُمنع الحذف الفيزيائي النهائي في المسار العادي.
- **FR-020**: يجب أن تستثني العروض/الاستعلامات الافتراضية الصفوف المحذوفة ناعمًا.

**بوابة المراجعة (مبدأ III)**

- **FR-021**: يجب فرض آلة حالات: مسودة → جاهز للمراجعة → مراجعة شرعية → اعتماد تحريري → منشور، مع حالتي "يحتاج تعديل" و"مرفوض".
- **FR-022**: يجب أن تُفرض التحوّلات المسموحة وصلاحيات كل دور في قاعدة البيانات (آلية حتمية)، لا كحقل اختياري.
- **FR-023**: يجب ألّا يستطيع أي دور — بما فيه المدير — تخطّي المراجعة الشرعية ثم الاعتماد التحريري قبل النشر.
- **FR-024**: يجب أن يرى الزائر (anon) المحتوى **المنشور فقط**.
- **FR-025**: يجب أن يسجّل النظام **هوية المُراجِع** الفعلي، وألّا تُعتبر المراجعة قائمة إلا بوجود مُراجِع مؤهّل مسجّل (R2).

**التدقيق الشامل (مبدأ IV)**

- **FR-026**: يجب أن تُسجَّل كل عملية إضافة/تعديل/حذف ناعم على جداول المحتوى في `audit_log` تلقائيًا.
- **FR-027**: يجب أن يلتقط كل صف تدقيق: العملية، القيمة القديمة والجديدة كاملةً (JSONB)، المستخدم، الوقت، الجدول، ومعرّف الصف.
- **FR-028**: يجب أن يلتقط التدقيق أدق التغييرات النصّية، بما فيها تغيير تشكيل حرف واحد.
- **FR-029**: يجب أن تُسجَّل أحداث دخول/خروج الإداريين في التدقيق.
- **FR-030**: يجب أن يكون `audit_log` **append-only**: لا UPDATE ولا DELETE عليه لأي دور بما فيه المدير، مفروضًا بالصلاحيات/السياسات.

**الأدوار والأمان (مبدأ VIII)**

- **FR-031**: يجب أن يدعم `profiles` أربعة أدوار: author/shariah_reviewer/editor/admin.
- **FR-032**: يجب فرض صلاحيات أقل-امتياز لكل دور عبر RLS.
- **FR-033**: يجب أن يستطيع المدير دعوة الأعضاء وتعيين/تغيير أدوارهم، وأن يُحصر ذلك به.
- **FR-034**: يجب أن تكون 2FA إلزامية لكل صاحب صلاحية كتابة/مراجعة/إدارة (جاهزية المخطط/السياسات لفرضها).

**الملاحظات والخطّافات (لبنة ٢٤, ٢٦, ٤٣)**

- **FR-035**: يجب أن يرتبط `content_notes` بأي كيان، مخفيًا عن الزائر افتراضيًا، مع حقل `is_public` لإتاحة النادر.
- **FR-036**: يجب أن يوفّر النظام **نقطة خطّاف** من سجل التدقيق لإشعارات الأحداث المهمة (دخول إداري، إدخال، رفع للمراجعة، اعتماد/نشر/رفض، اعتماد مرجع) قابلة للاستهلاك لاحقًا (تيليجرام).
- **FR-037**: يجب أن يوفّر النظام مسارًا قابلًا للجدولة لتصدير أسبوعي للسجلات/النسخ إلى وجهة خارجية (NAS).

**الحوكمة التشغيلية (مبدأ VII + توجيه المالك)**

- **FR-038**: يجب أن يمرّ كل تغيير على المخطط بملف migration مُدار في Git ويُطبَّق على Supabase السحابي عبر Supabase CLI؛ يُمنع تعديل المخطط بـ SQL مباشر يتجاوز Git (مثل لوحة Supabase أو أدوات MCP).
- **FR-039**: يجب كتابة اختبارات pgTAP فاشلة أولًا لكل متطلب قبل تنفيذه (TDD غير قابل للتفاوض).

**تنقيحات الجلسة التوضيحية (٢٠٢٦-٠٦-١٩)**

- **FR-040**: يجب أن يدعم مخطط م٠ نموذج ربط المعلومة بالنص متعدد اللغات كاملًا: ربط الإشارات داخل نص **كل لغة** بمعرّفات المعلومات (claims) المشتركة، واشتقاق ترقيم `[n]` لكل لغة من ترتيب الظهور — دون الحاجة لأي migration عند بناء المحرّر في م١. (المحرّر نفسه م١؛ المخطط الداعم م٠.)
- **FR-041**: يجب أن تكون كل قائمة ثابتة **جدولًا مرجعيًا** له `code` ثابت (المفتاح المرجعي) + تسميات مترجَمة لكل لغة + لون اختياري؛ ويجب أن تشير قواعد العمل وقيود CHECK وآلة الحالات إلى `code` لا إلى التسمية المعروضة.
- **FR-042**: يجب أن تكون جاهزية 2FA قائمة في م٠ (علَم حالة + سياسة RLS تتطلبها)؛ ويجب **تفعيل 2FA الكامل (TOTP) لكل عضو فريق حقيقي قبل أول دخول له** — شرط بوابة لا يُؤجَّل لما بعد م١.

### Key Entities *(include if feature involves data)*

- **events (حدث)**: عمود فقري؛ يحمل `timeline_order` وسنة تقريبية موقّعة وحالة مراجعة ونشر و`deleted_at`؛ نصوصه في جدول ترجمة.
- **persons (شخص)**: بروفايل كامل (يشمل النبي ﷺ)؛ حقول تمييز (نسب/كنية/وصف) لمعالجة تشابه الأسماء لاحقًا؛ نصوصه في جدول ترجمة.
- **locations (مكان)**: موقع بثقة مكان؛ نصوصه في جدول ترجمة.
- **sources (مصدر)**: كتاب/موسوعة معتمدة، يمرّ ببوابة اعتماد، ببطاقة درجة اعتمادية ومجال.
- **citations (استشهاد)**: موضع محدد داخل مصدر (مجلد/صفحة/رقم حديث).
- **claims (معلومة مفردة)** ⭐: حقيقة موثّقة؛ نوع، درجة توثيق، ترتيب ظهور، رابط حاوية واحد فقط، نص غني + `body_plain`؛ نصّها مترجَم في طبقة النصوص.
- **claim_citations**: ربط معلومة↔استشهاد بنوع علاقة.
- **event_persons / event_locations**: جداول ربط بين الأحداث والأشخاص/الأماكن.
- **profiles**: مستخدمون وأدوارهم وحالة 2FA؛ مرتبطة بمصادقة Supabase.
- **content_notes**: ملاحظات داخلية لأي كيان، مع `is_public`.
- **audit_log**: سجل append-only لكل العمليات وأحداث الدخول/الخروج (قديم/جديد JSONB).
- **جداول الترجمة (\*_translations)**: لكل كيان نصّي، بمفتاح (entity_id, lang)، حالة مراجعة وslug لكل لغة.
- **قوائم مرجعية**: درجة التوثيق، حالة المراجعة، ثقة التاريخ/المكان، نوع المعلومة، نوع علاقة الاستشهاد، الأدوار، اللغات المدعومة.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ١٠٠٪ من محاولات النشر التي تتخطّى المراجعة الشرعية ثم الاعتماد التحريري تُرفض (بما فيها محاولات المدير).
- **SC-002**: ١٠٠٪ من تعديلات المحتوى (حتى تغيير تشكيل حرف) تُنتج صف تدقيق واحدًا مطابقًا بقيمة قديمة/جديدة.
- **SC-003**: صفر عمليات UPDATE/DELETE ناجحة على `audit_log` لأي دور (بما فيه admin).
- **SC-004**: ١٠٠٪ من المعلومات المحفوظة تملك استشهادًا ودرجة؛ وصفر معلومات نوعها "حكم" بلا `grading_source`.
- **SC-005**: صفر معلومات بعدد روابط حاوية ≠ واحد (لا صفر ولا اثنان فأكثر).
- **SC-006**: الزائر (anon) لا يصل إطلاقًا لأي صف غير منشور (صفر تسريبات في اختبارات الصلاحيات).
- **SC-007**: ١٠٠٪ من الكيانات النصّية تملك `body_plain` مشتقًا ومتزامنًا مع نصّها الغني بعد الحفظ.
- **SC-008**: ترجمة غير منشورة لا تظهر بلغتها في أي مسار وصول (يُرجَع للعربية مع إشارة).
- **SC-009**: لا حذف فيزيائي: ١٠٠٪ من عمليات الحذف تُبقي الصف مع `deleted_at`.
- **SC-010**: كل متطلب وظيفي (FR) مغطّى باختبار pgTAP واحد على الأقل يفشل قبل التنفيذ وينجح بعده.
- **SC-011**: صفر تغييرات مخطط مطبّقة خارج ملفات migration المُدارة في Git.

## Assumptions

> تفاصيل تنفيذية اتُّخذت بافتراضات معقولة (غير سلوكية أو محسومة في القرارات)، تُراجَع في `clarify`/`plan`:

- **جداول الترجمة لكل كيان** (`event_translations`, `person_translations`, ...) بنمط (entity_id, lang) — **محسوم (س١، انظر Clarifications)** بدل جدول ترجمة متعدد الأشكال واحد.
- **اللغة الثانية مؤجّلة**: م٠ يبني العمود `lang` وقائمة لغات؛ الإدخال العربي أولًا؛ الإنجليزية (الأرجح) تُقرَّر وقت الترجمة (لبنة ٢٩).
- **صيغة النص الغني (rich JSON)** تُخزَّن كـ JSONB؛ البنية الدقيقة للإشارات داخل النص تُنضَج مع محرّر م١ — م٠ يضمن فقط التخزين واشتقاق `body_plain`.
- **آلية اشتقاق `body_plain`** (trigger مقابل عمود محسوب) تُحسم في plan.
- **آلية التدقيق** (trigger عام موحّد على الجداول) وتمثيل أحداث الدخول/الخروج (عبر خطّافات مصادقة Supabase) تُحسم في plan.
- **آلية فرض آلة الحالات** (trigger للتحوّلات + سياسات RLS للأدوار) تُحسم في plan.
- **خطّاف الإشعارات** في م٠ = التقاط الأحداث في التدقيق بشكل قابل للاستهلاك (مثلًا عبر Webhook/Edge Function لاحقًا)؛ التسليم الفعلي لتيليجرام في مرحلة لاحقة (لبنة ٢٦). يحتاج لاحقًا: توكن البوت + chat id.
- **تصدير NAS** = مهمة مجدولة (على VPS/NAS) تُعدّ وجهتها وقت التنفيذ (لبنة ٤٣).
- **فرض 2FA** يعتمد دعم Supabase Auth (TOTP)؛ م٠ يهيّئ المخطط/الأدوار وعلَم الحالة، والفرض التطبيقي الكامل يكتمل مع واجهة الإدارة.
- **2FA/المصادقة** تُدار عبر Supabase Auth؛ `profiles` يمتد جدول المستخدمين.
- **اسم المشروع** غير مزروع في المخطط؛ يبقى إعدادًا واحدًا.

## Out of Scope (مُتذكَّر للمراحل اللاحقة — لا يُنسى)

> ليست في م٠، لكنها مسجّلة هنا حتى لا تسقط، مع مرحلتها:

- **م١**: المحرّر الذكي وربط المعلومة بالنص والهايلايت الملوّن للإدخال (لبنة ١٩, ٣٣).
- **م٦**: صفحات العرض، النمطان (عامة/طالب علم) (لبنة ٢٣)، قسم الاستشهادات والعرض المزدوج.
- **سياسات تحريرية تُطبَّق وقت الإدخال/العرض** (تُحترم لكن لا تُبنى كجداول الآن): تسميات الدرجات للعرض (لبنة ٢١)، قواعد الصياغة حسب الدرجة (٢٢)، قاعدة عرض الأشخاص "غياب حدث ≠ نفي" (٢٧)، معايير الإدراج (٣٧).
- **مراحل لاحقة**: hadiths · verses · tags · media · relations · maps · search (م١٣) · diff والرجوع لنسخة سابقة · المساعد الذكي (م١١+) · المسارات التعليمية (م١٤).
- **التسليم الفعلي** لإشعارات تيليجرام واكتمال تكامل NAS (الخطّاف فقط من م٠).
